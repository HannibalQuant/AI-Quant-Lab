# AI QUANT LAB — Command Manual v1.0

**Document Class:** Constitutional Operating Manual  
**Authority:** AI Quant Lab Institutional Command Governance  
**Status:** v1.0  
**Applies To:** Every human, operator, executive, agent, workflow, connected-system, emergency, status, and archival command

## 1. Command Manual Philosophy

An institutional command is a governed transfer of intent and bounded authority into accountable work. Natural-language fluency, technical capability, urgency, or hierarchy cannot replace identity, scope, evidence, routing, constraints, and custody. Commands coordinate constitutional systems; they do not override them.

## 2. Command Principles

No command without identity, authority check, scope, intent, route, responsible agent, evidence requirements, expected outputs, completion criteria, prohibited interpretations and audit. No vague instruction becomes action. No silent amendment, reassignment, stage skip, evidence waiver or scope expansion. A command cannot convert evidence into decision, readiness into deployment, or capability into authority.

## 3. Command Identity Model

Every command receives immutable Command ID, record version, issuer identity/role, owner, type, intent, authority level, priority, urgency, created time and source. Amendments, retries, returns, escalation and follow-up link to the original but receive distinct versions or commands. Identity survives rejection, cancellation and archive.

## 4. Command Object Model

The record shall define command/owner/issuer/role/authority/responsible agent/workflow/type/intent/scope/status/priority/urgency/timestamps/deadline; all strategy, portfolio, artifact, evidence, memory, workflow, agent, DQS, IPS, XDS, VEP, RRP, EDP, DGS, MEDS, EDRP and PRC identities; market/capital/risk/deployment/monitoring scope; requirements, assumptions, ambiguities, clarification, constraints, prohibited actions/interpretations, authority checks, route, escalation, completion/return/rejection/challenge/cancellation criteria, output/decision summaries, limitations, contradictions, deviations, follow-up, institutional links and audit trail.

## 5. Command Lifecycle

**Proposed → Received → Identity Assigned → Authority Checked → Scope Checked → Intent Classified → Ambiguity Reviewed → Route Selected → Constraints Registered → Evidence Requirements Registered → Responsible Agent Assigned → Workflow Opened → Execution Authorized → In Progress → Status Reported → Output Produced → Output Reviewed → Completed → Returned → Rejected → Challenged → Cancelled → Archived**

Every transition records prior state, actor, authority, evidence, rationale, changed scope, conditions, output and time. Non-applicable operational states may be omitted only with explicit rationale; constitutional gates may not.

## 6. Command Authority Rules

Permitted authority levels are **REQUEST**, **RECOMMENDATION**, **WORKFLOW_INITIATION**, **WORKFLOW_CONTINUATION**, **EVIDENCE_SUBMISSION**, **VALIDATION_REVIEW_REQUEST**, **RISK_REVIEW_REQUEST**, **EXECUTIVE_DECISION_REQUEST**, **DEPLOYMENT_READINESS_REQUEST**, **DEPLOYMENT_ACTIVATION_REQUEST**, **MONITORING_ACTION_REQUEST**, **OPERATIONAL_CONTROL_ACTION**, **EMERGENCY_CONTAINMENT_ACTION**, **APPROVAL**, **REJECTION**, **SUSPENSION**, **REACTIVATION**, and **RETIREMENT**. Issuer authority, Agent Registry rights and governing standard must all permit the level and scope. Higher title does not create missing constitutional authority.

## 7. Command Scope Rules

Scope identifies object/version, purpose, market, venue, instrument, timeframe, regime, data, implementation, environment, capital, risk, deployment, monitoring, portfolio, workflow stage, time horizon, consumers and exclusions. Unspecified scope defaults to no institutional authority, not universal scope.

## 8. Command Intent Rules

Intent states the institutional outcome sought and distinguishes inquiry, recommendation, workflow initiation, evidence production, review, decision request, operational action, containment, status, cancellation and archive. Hidden secondary intent is prohibited. Multiple materially different intents become linked commands.

## 9. Command Routing Rules

Routing selects the governing standard, WOE workflow, eligible registered agent, dependencies, stage gates, upstream inputs, downstream consumers and escalation path. Route follows responsibility and authority, not convenience. Misrouted commands are returned or rerouted with an audit event.

## 10. Command Constraint Rules

Constraints preserve constitutional scope, evidence, versions, deadlines, resources, independence, prohibited actions, risk limits, deployment conditions, monitoring obligations, security/access and interpretation boundaries. A constraint conflict is surfaced before execution and resolved only by authorized amendment.

## 11. Command Ambiguity Rules

Ambiguity includes unknown object/version, unclear authority, incompatible intents, unstated stage, missing evidence, uncertain scope, conflicting terminology or implied approval. It is clarified, safely constrained, split or returned. Agents may make nonmaterial documented assumptions only when they cannot change authority, evidence, risk or lifecycle outcome.

## 12. Command Completeness Rules

A complete command contains identity, issuer and authority, intent, type, exact scope, responsible route/agent, required inputs/evidence, constraints, expected outputs, completion and rejection criteria, prohibited actions/interpretations, deadline where material and audit destination. Missing mandatory fields block authorization.

## 13. Command Rejection Rules

Reject, return or challenge commands lacking identity, authority, scope, owner, agent or evidence; containing hidden intent; requesting silent expansion, waiver, retuning, deployment, reactivation or monitoring override; converting research to Validation, Validation to risk, risk to Executive authority or readiness to deployment; conflicting with frozen evidence/limits/scope; bypassing DQS/IPS/EDP/DGS/PRC; or incapable of audit and reconstruction.

## 14. Command Challenge Rules

Any authorized participant may challenge identity, authority, assumptions, route, scope, evidence, conflicts, safety, feasibility or interpretation. Challenge freezes affected progression unless the governing standard permits safe containment, identifies owner and deadline, preserves contested evidence and records resolution or escalation.

## 15. Command Amendment Rules

Amendments state original command/version, changed field, reason, issuer, authority, timing, knowledge available, workflow/evidence impact, affected consumers and renewed acceptance. Material changes create a new version and may reopen authority, routing, evidence and stage gates. No retroactive amendment.

## 16. Command Cancellation Rules

Cancellation identifies authority, reason, affected workflows/agents/artifacts/evidence, safe stopping state, open obligations, notifications, retention and downstream effect. Cancellation stops future authority but never erases completed work, failures, decisions or custody.

## 17. Command Completion Rules

Completion requires expected outputs, criteria, evidence and artifacts delivered; limitations, contradictions, deviations and open questions stated; consumers notified; memory/workflow status updated; review completed; and audit closed. Completion is not Validation, risk approval, Executive approval, deployment authority or proof of edge.

## 18. Human Operator Command Rules

Human commands require registered identity/role, attributable intent and applicable authority. Operators may initiate requests and execute authorized controls but cannot bypass agent contracts or institutional gates. Informal conversation is noninstitutional until registered as a command.

## 19. Executive Command Rules

Executive commands may request review and issue only authority assigned by EDP/Agent Registry/governance. They cite VEP, RRP, unresolved issues, scope, conditions, expiry and monitoring. Executive urgency cannot rewrite evidence, risk review or implementation truth.

## 20. Agent Command Rules

Agents may issue commands only within registry rights, contracts, workflow roles and delegated bounds. Delegation identifies source, scope, duration and prohibited subdelegation. Agents cannot command approval of their own work or change their registry status.

## 21. Workflow Command Rules

Workflow commands identify WOE object, current stage/state, requested transition, gate evidence, owner, dependencies, blockers, expected artifacts, acceptance criteria and return path. A command cannot skip a stage merely because outputs appear available.

## 22. Research Command Rules

Research commands define question, context, scope, prior knowledge, evidence standard, uncertainty, falsifiability, prohibited conclusions, owner and handoff. They may generate research direction but cannot command a favorable answer, strategy approval or live use.

## 23. Market Discovery Command Rules

Commands cite universe, instruments/timeframes, DQS sources, observation period, scoring criteria, constraints and desired Market Opportunity Record. MDRS ranks research-worthiness and cannot issue entries, strategy edge or deployment claims.

## 24. Regime Classification Command Rules

Commands define exact market/timeframe/period/data, RCS taxonomy version, evidence, confidence/uncertainty requirements, transition handling and handoff. They cannot demand a preferred label or retrospective relabeling to preserve performance.

## 25. Feature Factory Command Rules

Commands state information need, FFS family, DQS inputs, scope, lineage, transformation review, leakage/bias/redundancy/stability requirements and intended use. They cannot select features solely for performance or treat feature output as edge.

## 26. Edge Discovery Command Rules

Commands define observed behavior, context, mechanism question, nulls, alternatives, feature/regime scope, costs, controls, sample/stability requirements and EDS handoff. They cannot request strategy rules, optimization-based edge or favorable classification.

## 27. Strategy Family Selection Command Rules

Commands cite frozen EDS, MDRS/RCS/FFS scope, candidate families, required comparison, mechanism/execution/cost/risk fit, limitations and architecture handoff. They cannot preselect a favored family or define entry/exit logic.

## 28. Strategy Architecture Command Rules

Commands identify strategy/family/edge versions, approved hypothesis, mechanism, information needs, modules, risk logic, failure modes, invalidation, experiment proposals and prohibited implementation changes. Architecture cannot be commanded to fit known backtest winners.

## 29. Engineering Command Rules

Commands cite approved architecture, exact implementation type/environment, DQS/FFS/RCS versions, IPS reference behavior, required outputs, fidelity tests, deviations and prohibited hypothesis changes. Engineering cannot be ordered to alter evidence or Validation conclusions.

## 30. Experiment Design Command Rules

Commands require XDS identity, purpose, scope, hypotheses/nulls, data partitions, variables/search space, costs, metrics, criteria, controls, reproducibility, deviations and EEP handoff before results. Confirmatory status cannot be commanded after observation.

## 31. Experiment Execution Command Rules

Commands cite frozen XDS and exact strategy/implementation/data/configuration versions, authorized runs, preservation of all outcomes, failures and deviations, stopping rules, custody and expected EEP. Execution cannot silently redesign the experiment.

## 32. Walk-Forward Command Rules

Commands cite XDS, WFRS window/partition/fold/reoptimization/aggregation plans, temporal integrity, costs, failure criteria and required handoff. They cannot request favorable windows, post-result repartitioning or selected fold reporting.

## 33. Monte Carlo Stress Command Rules

Commands define MCSTS inputs, dependency assumptions, perturbations, seeds, scenarios, severity, simulation count, thresholds, outputs and custody. They cannot request seed replacement, adverse-scenario exclusion or claim Validation from survival.

## 34. Parameter Stability Command Rules

Commands define PSS parameter/search scope, preregistered neighborhoods, interactions, boundaries, metrics, failure zones, WFRS/MCSTS context and handoff. They cannot ask for a robust island around a known winner after results.

## 35. Overfitting Defense Command Rules

Commands require complete research/data/holdout/candidate/feature/parameter/market/timeframe/regime/metric histories, ODS controls, complexity, multiplicity, deflation, PBO and penalties. Hidden failed trials or holdout reuse block completion.

## 36. Data Quality Command Rules

Commands define dataset/source/symbol/timeframe/period/purpose, DQS lineage, temporal/structural/market/preprocessing/revision/reconciliation checks, thresholds and eligibility output. They cannot order silent repairs or qualification from downstream performance.

## 37. Implementation Parity Command Rules

Commands cite reference behavior and exact target implementations, data, fixtures, calculation/signal/execution/state dimensions, preregistered tolerances and mismatch classification under IPS. Aggregate metric similarity cannot be the sole output.

## 38. Validation Command Rules

Commands request independent VEP review of frozen EEP and applicable WFRS/MCSTS/PSS/ODS/IPS/DQS evidence, exact scope, questions and required verdict. They cannot demand approval, suppress contradictions or broaden evidence.

## 39. Risk Review Command Rules

Commands cite issued VEP, exact strategy/portfolio/version/scope, assumptions, capital context and requested RRP. They require limits, controls, monitoring, kill/suspension/reactivation and open risks and cannot demand deployment authority.

## 40. Executive Decision Command Rules

Commands cite issued VEP/RRP, scope, target lifecycle action, open issues, conditions, monitoring and expiry and request EDP. They cannot command the Executive Agent to ignore blocks or rewrite scientific/risk evidence.

## 41. Portfolio Construction Command Rules

Commands define PCS purpose, candidate population, exact strategy versions, eligibility, allocation/risk-budget scope, exposures, dependence, liquidity/capacity, constraints, stress and monitoring. They cannot command diversification from low average correlation alone.

## 42. Production Readiness Command Rules

Commands cite target stage and exact strategy/portfolio/implementation/configuration/environment versions and request PRC review across every mandatory domain. They cannot convert paper readiness to live authority or waive missing controls.

## 43. Deployment Governance Command Rules

Commands cite issued EDP, PRC where applicable, exact DGS stage/scope/versions, readiness evidence, controls, owners, monitoring, kill and rollback. Activation remains a governed outcome, never an assumption embedded in the request.

## 44. Monitoring Command Rules

Commands define MEDS identity, deployed object/version, scope, baseline, metrics, thresholds, cadence, owners, alerts, escalation, evidence and health outputs. They cannot silently change thresholds or suppress adverse states.

## 45. Edge Decay Response Command Rules

Commands cite frozen MEDS trigger and request EDRP triage, severity, cause separation, authority and response. They may request containment but cannot order silent retuning, automatic reoptimization, reactivation or false-alarm dismissal.

## 46. Artifact Command Rules

Commands identify ART record/type/version/owner/purpose, requested create/freeze/supersede/deprecate/retire/archive action, authority, lineage, consumers, retention and outputs. Silent mutation or masquerading as current is prohibited.

## 47. Evidence Command Rules

Commands identify EES package/object, claim, scope, producer, provenance, admissibility, uncertainty, contradictions, custody, required validation/challenge and consumers. Evidence commands cannot convert evidence into verdict or remove limitations.

## 48. Memory Command Rules

Commands identify SMI object/type/version, authorized read/write/update, source evidence, owner, consumers, consistency and retention. Chat history and private model memory cannot substitute for a governed update.

## 49. Status Command Rules

Status output defines command/workflow identities, state, owner/agent, scope, completed and blocked steps, missing evidence, open questions, risks, next action, deadline, confidence, limitations and audit reference. It never implies approval absent an authority-bearing record.

## 50. Escalation Command Rules

Commands state triggering issue, severity, affected scope, current authority, failed route, evidence, requested higher authority, containment, owner, deadline and communication. Escalation does not expand the command while review is pending.

## 51. Emergency Command Rules

Emergency commands may initiate containment, trading pause, kill, exposure reduction, suspension, escalation, incident response, rollback request or monitoring-breach response. They define trigger, severity, scope, authority basis, immediate action, evidence freeze, owner, escalation, follow-up and prohibited interpretation. Containment may reduce risk before complete review but creates no new deployment authority.

## 52. Command Output Rules

Every output identifies command/version, workflow, producer, input/evidence versions, scope, completion status, artifact/evidence references, findings, limitations, contradictions, deviations, prohibited interpretations, downstream handoff and follow-up. Output classification is **COMMAND ACCEPTED**, **COMMAND ACCEPTED WITH LIMITATIONS**, **COMMAND NEEDS CLARIFICATION**, **COMMAND ROUTED**, **COMMAND RETURNED**, **COMMAND REJECTED**, **COMMAND CHALLENGED**, **COMMAND CANCELLED**, **COMMAND COMPLETED**, or **COMMAND INVALID**. Confidence is **HIGH**, **MEDIUM**, **LOW**, **INSUFFICIENT**, or **CONFLICTED**; maturity is **DRAFTED**, **REGISTERED**, **ROUTED**, **AUTHORIZED**, **IN_PROGRESS**, **OUTPUT_READY**, **REVIEW_READY**, **COMPLETED**, **RETURNED**, **REJECTED**, **SUPERSEDED**, or **ARCHIVED**.

### Readable Command Examples

**Example — Discover Markets:** Intent: rank research candidates in the registered crypto universe on 4H data. Scope: stated venues, symbols, period and DQS versions. Workflow: MDRS. Agent: Market Research Agent. Evidence: eligible DQS records and transparent scoring criteria. Output: Market Opportunity Records and ranking. Prohibited interpretation: high rank does not prove edge or deployability.

**Example — Request Validation:** Intent: obtain an independent scientific verdict for Strategy S, version 3. Scope: exact market, timeframe, regime and implementation. Workflow: VEP. Agent: Validation Agent. Evidence: frozen EEP with DQS, IPS, WFRS, MCSTS, PSS and ODS references. Output: issued VEP. Prohibited interpretation: an approved verdict is not risk or deployment approval.

**Example — Respond To Edge Decay:** Intent: contain and diagnose a material expectancy breach. Scope: exact deployment and portfolio versions. Workflow: EDRP. Agent: registered response owner with Risk escalation. Evidence: frozen MEDS trigger, baseline and affected records. Output: severity, cause path, authorized action and follow-up. Prohibited interpretation: recent recovery does not reactivate authority.

**Example — Activate Paper Monitoring:** Intent: activate forward observation without live capital. Scope: exact strategy, implementation, data, configuration and authorized regimes. Workflow: EDP/DGS/MEDS. Agent: deployment governance. Evidence: issued paper authority, PRC, controls and baseline. Output: Paper Monitoring Activation Record. Prohibited interpretation: paper operation does not authorize limited live.

## 53. Command Audit and Reconstruction

An independent reviewer must reconstruct issuer, authority, intent, scope, ambiguity, route, constraints, evidence, assigned agent, workflow states, amendments, outputs, reviews, completion/cancellation and consumers without chat history or private memory. Audit preserves records, versions, timestamps, signatures/attribution, custody, challenges and archive.

## 54. Integration with MACP

MACP is the governed transport for commands and responses. Every institutional command cites Command ID/version, sender/recipient rights, type, authority, scope, workflow, evidence, urgency, constraints and acknowledgement. Conversation alone cannot substitute for MACP registration.

## 55. Integration with SMI

SMI stores current command state, scope, owner, route, dependencies, blocks, deadlines, outputs and institutional references. Commands read/write only authorized objects; conflicting or stale state blocks continuation.

## 56. Integration with EES

EES governs evidence requested, submitted, transferred, challenged and consumed by commands. Commands preserve provenance, admissibility, uncertainty, contradictions, freeze, custody and limitations and cannot waive evidence obligations.

## 57. Integration with WOE

WOE opens, routes and controls command-backed workflows, owners, stage gates, dependencies, statuses, returns, escalation, cancellation and archive. Command completion and workflow completion are both required where linked.

## 58. Integration with Agent Registry

AR determines eligible agent identity, status, contract, message rights, memory/evidence rights, workflow eligibility, delegation and authority. Commands cannot expand these rights or assign suspended/retired agents institutional work.

## 59. Integration with Artifact Registry

ART registers every command-created or changed artifact and links command, producer, workflow, evidence, versions, consumers, freeze, supersession, retention and archive. Commands cannot silently mutate frozen artifacts.

## 60. Integration with Strategy Lifecycle Standard

SLS determines valid strategy state and transitions. Commands request but cannot presume lifecycle advancement, suspension release or retirement; exact strategy version and governing decision are mandatory.

## 61. Integration with Autonomous Research Pipeline

ARP commands define pipeline identity, stage, owner, evidence/artifact handoffs, return path and learning output. Silent stage/agent/evidence substitution or scope expansion is prohibited.

## 62. Integration with Data Quality Standard

DQS commands govern source registration, review, eligibility, quarantine, remediation and revision. Any data-dependent command cites exact DQS and dataset versions and inherits limitations.

## 63. Integration with Feature Factory Standard

FFS commands bind feature purpose, identity/version, lineage, scope, reviews and use rights. No command may introduce an unregistered feature into institutional evidence or live operation.

## 64. Integration with Regime Classification Standard

RCS commands bind taxonomy, evidence, scope, confidence, uncertainty, transitions and handoffs. Preferred labels and post-performance relabeling are invalid command intents.

## 65. Integration with Edge Discovery Standard

EDS commands preserve observed behavior, mechanism, nulls, alternatives, controls, costs, evidence and classifications. They cannot issue strategy, Validation or deployment authority.

## 66. Integration with Strategy Family Selection Standard

SFSS commands require frozen edge context, candidate alternatives, fit reviews, limitations and architecture handoff. Selected family cannot be silently changed downstream.

## 67. Integration with Experiment Design Standard

XDS commands preregister identity, scope, hypotheses, data, variables, assumptions, metrics, controls, criteria, deviations and outputs before interpretation. Post-result changes create amended exploratory work.

## 68. Integration with Walk-Forward and Robustness Standard

WFRS commands bind temporal partitions, window logic, folds, reoptimization, aggregation, failure and reporting. They cannot select favorable folds or redesign after results while retaining confirmatory status.

## 69. Integration with Monte Carlo and Stress Testing Standard

MCSTS commands bind inputs, dependencies, perturbations, seeds, scenarios, thresholds and full reporting. Stress requests cannot omit unfavorable scenarios or convert simulation into authority.

## 70. Integration with Parameter Stability Standard

PSS commands bind search spaces, neighborhoods, interactions, boundaries, failure zones and classification. They cannot request post-result islands around selected parameters.

## 71. Integration with Overfitting Defense Standard

ODS commands require complete search/exposure histories, controls, complexity, multiplicity, deflation and penalties. Command history itself becomes part of research-path transparency.

## 72. Integration with Implementation Parity Standard

IPS commands bind reference and target versions, DQS inputs, event-level dimensions, fixtures, tolerances and mismatch outputs. Non-equivalent implementations cannot support the same claim by command fiat.

## 73. Integration with Experiment Evidence Package

EEP commands require frozen design, all runs, controls, failures, deviations, limitations and reproducibility. Packaging cannot be commanded to omit adverse evidence.

## 74. Integration with Validation Evidence Package

VEP commands request independent review with exact evidence and scope. They cannot prescribe verdict, remove limitations or convert Validation to risk/deployment authority.

## 75. Integration with Risk Review Package

RRP commands request exact risk review based on issued VEP and portfolio/capital context. They cannot prescribe acceptance or omit limits, monitoring, kill, suspension and open risks.

## 76. Integration with Executive Decision Package

EDP commands request a governed verdict with VEP/RRP and unresolved issues. Only registered Executive authority may issue approval, return, rejection, suspension, reactivation or retirement within constitutional bounds.

## 77. Integration with Portfolio Construction Standard

PCS commands bind exact candidate population, versions, allocation/risk budgets, exposures, dependencies, constraints, stress and monitoring. They cannot command diversification or capital authority from component performance.

## 78. Integration with Deployment Governance Standard

DGS commands bind EDP authority, stage, exact locks, readiness, owners, controls, monitoring, kill and rollback. Requests and preparations cannot masquerade as activation records.

## 79. Integration with Monitoring and Edge Decay Standard

MEDS commands bind monitored object, baseline, thresholds, states, cadence, owners, alerts, evidence and escalation. Monitoring obligations cannot be silently disabled or weakened by status/operation commands.

## 80. Integration with Edge Decay Response Playbook

EDRP commands bind frozen trigger, severity, affected scope, causes, authority, action, returns, revalidation, reactivation and retirement. Emergency containment may reduce authority but cannot create it.

## 81. Integration with Production Readiness Checklist

PRC commands bind exact target stage/scope/versions and every readiness domain, gap and exception. A readiness request or classification cannot itself activate paper, limited live or live active operation.

## 82. Governance

Institutional command governance owns this manual, command taxonomy, identity, routing and audit. Domain standards retain substantive authority; AR retains agent authority; WOE controls workflow; EDP/DGS govern decision and activation. Changes require versioning, impact analysis, approval and migration. Exceptions are scoped, owned, time-bounded and auditable and cannot waive identity, authority, constitutional gates, custody or reconstruction.

Mandatory command types include research, every market-to-monitoring stage, artifact/evidence/memory/status/escalation/emergency/cancellation/archive. Mandatory dimensions include identity, authority, scope, intent, priority, urgency, owner, route, evidence/input/output/data/artifact/memory/Validation/risk/decision/deployment/monitoring/portfolio requirements, constraints, prohibitions, completion and auditability.

Every future AI Quant Lab human, operator, executive, agent, workflow, system, emergency, status or archive instruction must conform to CM before institutional reliance. Failed, rejected, challenged, cancelled, invalidated, superseded and archived commands remain learnable and reconstructable.
